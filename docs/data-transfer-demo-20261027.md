# A100 ↔ RTX 5090 数据通道验收（2026-10-27）

## 结论

已经打通**按需 SSH + rsync 文件交换**，由 A100 发起双向操作，适合训练工作流的小规模数据下发、结果回收 Demo。不是跨机高速训练互联或共享存储，也没有把前端按钮接入真实作业调度。

复用现有 Tencent / Windows 路线，不新增服务、端口、网卡、路由或代理。短测 A100 → 5090 约 **11.42–13.63 Mbps**，5090 → A100 约 **1.74–2.16 Mbps**。高流量测试期间出现过一次 5090 新 SSH 握手超时，日常默认值因此设为 **128 KiB/s**；随后限速双向测试期间，8 轮 × 3 台机器的 SSH 检查 **24/24 成功**。不能将本次结果描述为“完全不占用原 SSH 带宽”或“长期零故障”。

操作与原始指令见 [完整使用说明](../ops/data-transfer-demo/README.md)，客户端源码为 [transfer.py](../ops/data-transfer-demo/transfer.py)。

## 真实拓扑与变更范围

- A100：`aiusr@192.168.2.201:2202`，维护登录仍使用腾讯云 ProxyJump + 原 OpenVPN。数据发送则由 A100 主动连接腾讯云公网 22。
- 5090：`user001@192.168.1.111:22`，维护入口仍为腾讯云 `127.0.0.1:2223`，经过原研究院 Windows 反向中转。
- 数据通道：A100 专用 SSH 客户端 → 腾讯云受限强制 `nc 127.0.0.1 2223` → 原 Windows 通道 → 5090 目录受限 `rrsync`。内层 SSH 对 A100 与 5090 之间的数据加密。腾讯云不存数据副本。
- 两台 GPU 机器分别尝试直连对端私网 SSH 端口，4 秒内未连接成功；因此没有把两个不同私网段当成可直连网段，也没有修改路由来尝试打通。
- 笔记本只用于本次部署与观测，数据传输在服务器端运行；复用原路线意味着 **Windows 中转机必须在线**。

实际只新增两行受限公钥（云端 ubuntu、5090 user001 各一行）、A100 的独立客户端配置与密钥、两端 Demo 目录。没有安装软件包、升级系统、启动 GPU 作业、重启 SSH/Nginx/VPN/机器，也没有改动原业务数据。

## 吞吐测试方法与结果

北京时间约 **19:18–19:32**。使用操作系统随机字节生成的合成数据，不接触真实训练集；SSH 和 rsync 均不压缩，避免零填充/压缩制造虚高带宽。两方向每轮使用不同目录，确认 `Literal data` 确实传输了全量。速度为应用层有效吞吐，包含建立连接、rsync 与校验等开销，不是网卡线速。MB/Mbps 使用十进制，MiB 使用 1024² 字节。

### 三轮 8 MiB 短测（显式取消带宽上限）

| 方向 | 第 1 轮 | 第 2 轮 | 第 3 轮 | 按总数据/总时间合计 |
| --- | --- | --- | --- | --- |
| A100 → 5090 | 5.875 s / 11.422 Mbps | 5.274 s / 12.724 Mbps | 4.925 s / 13.627 Mbps | **12.525 Mbps / 1.493 MiB/s** |
| 5090 → A100 | 38.479 s / 1.744 Mbps | 31.022 s / 2.163 Mbps | 32.976 s / 2.035 Mbps | **1.965 Mbps / 0.234 MiB/s** |

这只是当时现网条件下的三次样本。速度明显非对称，可能受跨网出口、原 Windows 通道及链路拥塞等共同影响；没有足够隔离测试来把瓶颈归因于某一网卡、服务器或运营商。

### 大文件与断点续传

- A100 → 5090：64 MiB，先以 512 KiB/s 运行，8 秒后只中断本次 Demo 的进程组。再次运行时匹配复用 **2,783,872 字节**，新传 **64,324,992 字节**，剩余传输 **125.298 秒**，退出码 0。
- 5090 → A100：64 MiB，上限 512 KiB/s，完成时间 **280.825 秒**，有效 **1.912 Mbps**，退出码 0。
- 高流量阶段出现的登录问题使我们决定停止此档位；发出停止命令时，反向大文件已于 **19:27:40** 自然传完，因此没有删除或重启原 SSH 进程。
- 以上 8 个数据集均独立验证 SHA-256 一致。续传只验证了受控中断后的恢复，没有模拟整机断电或拔网线。

### 最终默认限速复验

运行不带 `--bwlimit` 的最终脚本，默认 **128 KiB/s ≈ 1.05 Mbps**：

| 方向 | 文件 | 时间 | 结果 |
| --- | --- | --- | --- |
| A100 → 5090 | 新 8 MiB 数据集 | 67.332 s | 退出码 0 |
| 5090 → A100 | 新 8 MiB 数据集 | 68.644 s | 退出码 0 |

同期 8 轮 SSH 登录分别访问云端、A100、5090，全部 24 次成功。完整连接并执行 hostname 的耗时：云端 **0.508–0.605 s**、A100 **2.381–2.841 s**、5090 **1.498–3.740 s**。这些是 SSH 命令用时，不是 ping 延迟。只对当前负载与短期窗口有效；共享物理网络仍可能竞争。

两个限速样本也通过独立 SHA-256 校验。5090 另外生成 `result-demo-001/result.json`，记录 5 个接收样本的校验状态，并明确 `training_started: false`；已从 A100 拉回并校验成功。这个例子演示了“数据下发 → 目标端校验 → 结果回收”的完整流程，没有占用 GPU。

## 稳定性与局限

| 从 GPU 服务器 ping 腾讯云公网 | 样本 | 丢包 | RTT 最小/平均/最大 | P95 |
| --- | --- | --- | --- | --- |
| A100 | 545 发 / 539 收，约 545 秒 | **1.10%** | 4.278 / 6.158 / 20.656 ms | 13.7 ms |
| 5090 | 600 发 / 591 收，约 600 秒 | **1.50%** | 24.983 / 25.807 / 31.119 ms | 26.7 ms |

这两条是各端至腾讯云的 ICMP 探测，**不是 A100 到 5090 端到端 ICMP**，5090 的直接 ping 也不经过 Windows 反向 SSH 路线。ICMP 可能被限速，不能把其丢包率直接等同为 TCP 文件丢包率；文件完整性由接收端 SHA-256 验证。

高流量长测时有一次 15 秒超时设置下的新 5090 SSH 握手失败（`Connection timed out during banner exchange`）；原端口监听及隧道 PID 没变，后来正常登录恢复。无法仅靠这个事件证明唯一根因，但说明不宜继续用较高并发/不限速数据流争用此中转。后续默认限速检查没有复现握手失败。

业务意义：适合小样本数据分发、配置下发及结果回传。按短测速度理想连续传输 **100 GB**，正向约 **17.7 小时**、反向约 **4.7 天**，还没计入并发、断线和日常限速。因此不能依靠这条 Demo 通道证明“量产大数据持续搬运”或跨机同步训练带宽达标。演示宜预先在目标机放好数据，按版本增量同步，并让训练读取目标机本地数据；跨机梯度同步不在此次方案中。

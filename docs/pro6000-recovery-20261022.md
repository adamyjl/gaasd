# PRO 6000：第二次卡死与 SSH 恢复

2026-10-22，北京时间。用户报告 10 月 21 日约 22:40 再次卡死；这次鼠标仍能移动，ToDesk 显示在线但不能正常进入。10 月 22 日重启后仍无法经 SSH 登录，手工将 ZeroTier MTU 调为 1280 后成功。

## 已确认的三个问题

### 1. 系统内核异常再次发生

上一启动 journal 在 **2026-10-21 22:38:33** 记录 `BUG: kernel NULL pointer dereference, address: 0000000000000650`。EFI pstore 保留更完整的异常：第一个 Oops 位于 `__lruvec_stat_mod_folio+0x62/0xf0`，执行上下文为 `kworker/u96:1`，工作队列为 `writeback wb_workfn (flush-259:3)`，栈经过 ext4 写回；随后 systemd-journal、htop、sshd 等执行上下文出现 Oops/Bad page state。至少记录到 Oops #8。

这些记录支持内核内存管理异常再次发生；鼠标能移动、ToDesk 显示在线并不能排除系统部分卡死。不能据执行进程名认定 ToDesk、Firefox、htop 或监控探针是根因，也不能仅凭写回栈认定 SSD 或数据盘挂载造成故障。具体是 RAM/内存控制器/主板/固件，还是内核/驱动破坏内存，仍待硬件诊断及受控复现。

另有 ToDesk 4.9.7.0 的 SIGSEGV crash，时间为 **10 月 22 日 10:16:04**，发生在本次重启之后，不能把它当作昨晚 22:38 的首发原因。

### 2. ZeroTier MTU 设置没有持久化

检查时虚拟接口 `ztr2q7djxe` 的 MTU 已被用户手工设为 1280，但对应 service/timer 尚不存在。已安装本项目中的 `pro6000-zerotier-mtu.service` 与 `.timer`：开机后 10 秒首次触发，并在每分钟 00/30 秒检查；接口存在且 MTU 非 1280 时才修改。没有修改物理网卡 MTU或其他节点。

验证：11:32:03 将该虚拟接口 MTU 暂改为 1300，11:32:30 定时任务恢复 1280。普通 `ssh lenovo@10.243.216.196` 已成功，不需要 `-F none`、`-vv` 或 `IPQoS=none` 才能完成本轮测试。没有声称已经定位整个 ZeroTier 路径的真实 PMTU；1280 是现场验证有效的规避设置。

### 3. 腾讯云旧反向隧道占用端口

腾讯云 `127.0.0.1:2226` 仍由 10 月 21 日 20:07:36 建立的旧隧道会话监听，积累大量未处理连接。开发机重启后新隧道报 `remote port forwarding failed for listen port 2226`，重试超过 400 次。原云端有效配置为 `ClientAliveInterval 0`。

已只在 `Match User gaasd-pro6000-tunnel` 内添加：

```text
ClientAliveInterval 20
ClientAliveCountMax 3
```

`sshd -t` 和指定用户的 `sshd -T -C` 检查通过，reload 后核对并清理了两个明确属于该旧隧道的进程。开发机原有 20 秒/3 次客户端心跳、10 秒 systemd 重试保留。云端与开发机双向失联检测减少卡死后旧监听长期滞留的问题；这不是整机卡死修复。原 2222–2225 等其他通道未修改。

新隧道已恢复，并再次主动 restart 验证恢复。此命令重新可用：

```sh
ssh -J ubuntu@49.232.60.144 -p 2226 lenovo@127.0.0.1
```

云端监控 `connection.json` 已回到 `ok: true`，PRO 6000 的快照和历史继续更新。

## 登录提示与启动兼容性

### Failed to connect

来自 `/var/lib/ubuntu-release-upgrader/release-upgrade-available` 中缓存的 `Failed to connect to https://changelogs.ubuntu.com/meta-release-lts`。这是 Ubuntu 发行版更新查询的错误，不是 SSH 公钥认证失败。

已验证该 HTTPS 地址返回 200，并重新运行系统自带 `check-new-release -q`，退出码 0。缓存已按真实查询结果刷新为新发行版提示，没有关闭更新检查或通过清空文件隐藏错误。本次未执行 `do-release-upgrade`。

### 需要重启系统

这是有效的更新提示。APT 历史显示 **10 月 22 日 10:59～11:08 的 unattended-upgrade** 更新了 libc 等包，并在 11:03 安装 `linux-image-7.0.0-38-generic`。因此这些更新发生在昨晚卡死之后，不能解释昨晚首发故障。

当前仍运行 `6.11.0-17-generic`。NVIDIA 595.58.03 通过安装器手工安装，现有模块只覆盖 6.11；机器没有 DKMS，`modinfo -k 7.0.0-38-generic nvidia` 返回模块不存在。新内核和 initramfs 已存在，原 GRUB 默认 0 会选新内核，显卡启动兼容性尚未通过。

为避免下一次直接启动到缺少 NVIDIA 模块的内核，已暂时写入 `/etc/default/grub.d/90-pro6000-driver-compat.cfg`，按本机实际 GRUB 菜单 ID 选择 6.11，并显示 5 秒启动菜单。`update-grub`、`grub-script-check` 通过；GRUB 没有一次性 next_entry 覆盖。

这只是临时启动兼容性保护，不代表 6.11 的稳定性通过，也不是长期固定旧内核的方案。新内核应先配齐并验证同版本 NVIDIA 模块、initramfs 和 Secure Boot 条件，再移除此 drop-in 并重新 `update-grub`。机器已重复出现内核崩溃，应与供应商的内存/平台诊断一并安排，不宜在缺少现场恢复手段时直接进行系统大版本升级或替换显卡驱动。

`/run/reboot-required` 保留，没有伪造清除。本轮没有重启整机、运行压力测试或安装/卸载驱动。尚未完成重启验收，因此不能承诺下次不会再次发生内核故障。

## 验证、证据和回退

已完成 systemd 单元语法校验、四个相关服务/定时器的 enabled/active 检查、MTU 自动纠正实测、两条路线的 SSH 公钥登录、隧道 restart 恢复、云端有效 SSH 配置核验、监控成功采集、GRUB 语法及目标菜单核验。未进行网页改版或业务前后端发布。

本地原始证据：`work/pro6000-recovery-20261022/`（Git 忽略）。PRO 6000 和腾讯云分别使用 `/var/backups/gaasd-pro6000-recovery/20261022/` 保存本机相关证据与修改前配置。原始日志、ToDesk crash、BERT 和运行数据不提交公共仓库。

- MTU 规则：`systemctl disable --now pro6000-zerotier-mtu.timer` 停止后续自动修改；不会自动恢复旧 MTU。回退 MTU 前确认有腾讯云备用入口。
- 云端心跳：只撤销该用户 Match 块内新增的两行，校验后 reload；不要在配置有后续修改时整文件覆盖。
- 启动项：新内核驱动验证通过后移除临时 `90-pro6000-driver-compat.cfg`，`update-grub` 并核对结果；保留旧内核作回退。

参考：[systemd timer](https://www.freedesktop.org/software/systemd/man/latest/systemd.timer.html)、[OpenSSH ClientAlive](https://man.openbsd.org/sshd_config#ClientAliveInterval)。
